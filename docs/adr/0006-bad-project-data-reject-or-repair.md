# 6: 坏工程数据分两类处理——结构性错误拒绝，可修字段修好并告知

读工程（文件导入、IndexedDB、复制）只有一条校验入口 `validateProject()`。它把问题分成两类：

- **结构性错误直接拒绝**：schemaVersion 不认识、格子数据解压失败或长度不符、板阵非法（未知板型 / 重叠 / 超限）、画布尺寸不是正整数、格子引用了色板里不存在的色号。这些一旦猜错就会产出"看着正常但物理上做不出来"的图。
- **可修字段就地修好并在提示里说清楚**：时间戳/视图/跟做进度格式不对、色号白名单里有不存在的色号、板外空档里有脏格子、色板 id 不认识。这类问题的正确修复是唯一确定的，拒绝导入只会让用户丢掉整份作品。

两条特别约定：

- **空档里的脏数据清除后要报数**（"板外的空档里有 N 格脏数据，已清掉"）。静默清理等于把上游的 bug 藏起来。
- **不认识的色板 id 不静默回退**：换成默认色板**并提示"找不到色板 X，已临时改用 Y"**。静默回退会让同一堆色号索引被另一套色解释，图上颜色全错而用户毫不知情。

## Considered Options

- **一律拒绝**：数据最干净，但一个坏时间戳就能让用户打不开自己的作品。
- **一律尽力修复**：用户永远打得开，但板阵非法这类错误会被"修"成一张错误的图纸，代价是几百颗豆。
- **按上面两类分开 ← 选定**。分界线是"修错了会不会产出物理上做不出来的东西"。
- **未知色板静默回退到第一套色板**（原实现）：最省事，但颜色错得无声无息。

## Consequences

- `parseProject()` 只是 `JSON.parse` + `validateProject()`，IndexedDB 里的对象也过同一个函数——两条读路径不可能再出现校验不一致。
- `ParseResult.error` 的 `recovered` 分支现在可能带多条提示（用"；"连起来）。界面必须能显示它，不能只把它当成功丢掉。
- 导入界面不再需要自己先解析 JSON 去猜色板大小：色板 id 与色号范围由校验器自己查。
